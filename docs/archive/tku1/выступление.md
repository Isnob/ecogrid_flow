## Слайд 1. Богдан — общая характеристика проекта

Здравствуйте! Мы команда «Шпингалеты», проект EcoGrid Flow. Я Богдан, тимлид и Product Owner.

Компании, у которых свои дата-центры, запускают тяжёлые задачи — обучение моделей, ночные ETL-пайплайны — по жёсткому расписанию. А цена электроэнергии на бирже за сутки меняется в разы, и от погоды зависит, сколько энергии уходит на охлаждение. В итоге компания переплачивает.

Наш сервис берёт цены с биржи ENTSO-E и прогноз погоды Open-Meteo, проверяет их качество и рассчитывает, когда и в каком дата-центре запустить задачу дешевле всего, не нарушив дедлайн. Результат отдаём через REST API — его вызывает оркестратор Airflow — и через веб-симулятор.

Пользователи — дата- и ML-инженеры и финансовый директор. Команда — пять человек, роли и зоны ответственности в таблице. Дальше Арина расскажет про предметную область и данные.

## Слайд 2. Арина — предметная область и источники данных

Сейчас тяжёлые задачи стартуют по cron в один и тот же час и всегда в одном дата-центре — цена и погода не учитываются. С нашим сервисом время старта подбирается как самое дешёвое окно до дедлайна, дата-центр выбирается из трёх, а охлаждение считается по прогнозу погоды.

Главные заинтересованные стороны: дата-инженеру нужно не сорвать дедлайн и быстрый ответ API, финансовому директору — экономия в евро, службе безопасности — чтобы данные не уходили наружу.

В таблице — каталог источников: цены ENTSO-E в XML раз в сутки, прогноз Open-Meteo в JSON каждые три часа, и два внутренних — справочник дата-центров и параметры задачи из Airflow.

Проблемы данных, которые мы ожидаем: биржа может задержать публикацию, бывают пропуски интервалов, дубли, смена шага цен с часа на 15 минут и аномальные цены. Это ловит проверка качества, а если свежих цен нет — работает запасной режим. Контекстная диаграмма есть в запасных слайдах.

## Слайд 3. Григорий — требования и качество данных

Мы составили 38 проверяемых требований: 18 функциональных — что система делает, 13 нефункциональных — насколько хорошо, и 7 требований к данным. В таблице основные. Например, загрузка цен раз в сутки, проверка качества данных, окно не выходит за дедлайн, ответ API быстрее 200 миллисекунд, и наружу сервис ходит только к двум источникам. Требование к данным DR-01: 24 или 96 значений цены в сутки на зону, точный тип numeric и хранение 5 лет.

Приоритеты расставили по MoSCoW: 17 обязательных — без них нет релиза.

Справа — критерий приёмки, который можно проверить на тестовых данных: если в партии цен есть значение 9999 евро за мегаватт-час, эта строка не попадает в базу, в журнал пишется ошибка с кодом, а загрузка продолжает работать. Этот тест должен пройти к контрольной точке 23 октября.

Ключевой сценарий — оркестратор Airflow перед запуском пайплайна спрашивает наш API и получает время и дата-центр. Дальше Максим расскажет, как мы организовали работу.

## Слайд 4. Максим — организация разработки

Мы работаем по Kanban в «Сфере». Выбрали его, потому что загрузка у студентов неравномерная — спринты постоянно срывались бы. Работаем потоком, и у каждого в работе не больше одной задачи.

Бэклог устроен как Epic → Feature → Task: пять эпиков — загрузка данных, хранение, ядро, бэкенд и веб. Например, эпик «хранение», в нём фича «инфраструктура базы», в ней задача «PostgreSQL в Docker» — она выполнена. Справа — наша настоящая доска: восемь задач в работе, шесть решено.

Задача считается готовой, только если код в репозитории, прошёл ревью и тесты и ветка влита. В Git — ветка от develop, Merge Request с одобрением, потом в master на релизе.

Внизу — контрольные точки до Release 0.5: каждые две недели, ближайшая — 23 октября, релиз — 18 декабря.

Главный риск по данным — мой: загрузка пока работает на ноутбуках, и к релизу может не набраться 14 дней без сбоев. Решение — постоянно включённый компьютер, догрузка пропусков и ежедневная сверка полноты. Дальше Александр расскажет про архитектуру.

## Слайд 5. Александр — архитектура и поток данных

Сверху — поток данных. Источники — цены ENTSO-E в XML и погода Open-Meteo в JSON. ETL-воркер забирает их по расписанию, дальше проверка качества: полнота, дубли, допустимый диапазон цен. Потом приводим всё к UTC и единому шагу, считаем PUE и сохраняем в PostgreSQL. Результат выдаём через REST API и веб.

Внизу — предварительная схема контейнеров C4. Всё работает в Docker Compose внутри сети клиента: воркер загрузки, база, API вместе с ядром расчёта и веб. Наружу ходит только воркер и только к двум адресам. Airflow клиента и веб обращаются к API по REST с токеном, ошибки возвращаются в едином формате с кодом.

Почему так: данных немного — около двухсот тысяч строк цен в год, поэтому Big Data не нужен, хватает PostgreSQL с партициями по месяцам. FastAPI с NumPy даёт ответ быстрее 200 миллисекунд. Если строка плохая — она уходит в журнал проверки, если свежих цен нет — работает запасной режим.

Уже работает: база PostgreSQL 16 в Docker Compose. Дальше Богдан подведёт итоги.
