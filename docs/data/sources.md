## 2. Обоснование выбора исторических источников

Для исторических цен и структуры генерации выбран **ENTSO-E Transparency Platform**, потому что он публикует временные ряды по энергозонам и отдельные данные по Day-Ahead ценам и типам генерации в машиночитаемом формате. Источник подходит для EDA и дальнейшей подготовки признаков ML-модели.

Для исторической погоды выбран **Open-Meteo Historical Weather API**: он принимает координаты, даты и список погодных переменных, а архивные данные доступны за длительный период. Это позволяет связать погоду с конкретным ЦОД через координаты.

Исторические ряды необходимо импортировать в таблицы `entsoe_day_ahead_prices`, `entsoe_day_ahead_generation` и `open_meteo_historical_weather`. Перед ETL нужно проверить через выданный токен ENTSO-E доступность нужного периода и выбранных энергозон.

> [!WARNING]
> Доступ к источникам различается. Для ENTSO-E нужны регистрация, роль Web API Consumer и Security Token. Для Open-Meteo некоммерческого использования ключ обычно не требуется. Таблицы `datacenters`, `jobs` и `recommendations` зависят от доступа к внутренней инфраструктуре клиента.

## 3. Как загружаются данные

* **Сбор:** сервис `etl-worker` (`services/etl/`). Сейчас загружается погода: прогноз — каждые 3 часа (`scheduler.py`), архив — разовым запуском `run_historical_weather.py`. Загрузчик цен ENTSO-E появится после получения токена.
* **Запись:** идемпотентная, `INSERT … ON CONFLICT … DO UPDATE` — повторная загрузка не создает дублей.
* **Время:** перед записью все метки приводятся к UTC.
* **Единицы:** цены ENTSO-E — EUR/MWh, генерация — MW; единицы проверяются при импорте.
* **Происхождение:** у каждой строки хранится время загрузки `retrieved_at`. Источник однозначно определяется таблицей, поэтому отдельное поле `source` не хранится.
* **Качество:** диапазоны значений проверяет Python-слой до записи, а не `CHECK`-ограничения в БД (см. [ERD, п. 4](ERD.md)).
