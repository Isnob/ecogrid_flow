## 1. Функциональные требования (Functional Requirements — FR)

Формулировки составлены в стандарте RFC 2119 (ДОЛЖНА / SHALL).

| ID | Категория | Связанные сценарии | Описание требования |
| :--- | :--- | :---: | :--- |
| <a id="fr-api-01"></a>**FR-API-01** | API Gateway | UC-01, UC-02 | Система ДОЛЖНА предоставлять эндпоинт `POST /api/v1/recommendations`, принимающий параметры задачи: `job_id` (UUID/str), `duration_minutes` (int > 0), `required_power_kw` (float > 0), `deadline` (ISO 8601 UTC), `earliest_start` (ISO 8601 UTC, опционально, default: now), `allowed_zones` (список строк), а также опциональные параметры базового сценария `preferred_datacenter_id` (default: ЦОД первой зоны из `allowed_zones`) и `baseline_start` (ISO 8601 UTC, default: `earliest_start`). Если `preferred_datacenter_id` не входит в `allowed_zones` или `baseline_start` выходит за интервал [`earliest_start`; `deadline − duration_minutes`], запрос отклоняется с кодом `422 Unprocessable Entity`. |
| <a id="fr-api-02"></a>**FR-API-02** | API Gateway | UC-01 | Система ДОЛЖНА выполнять валидацию дедлайна и отклонять запрос с HTTP-статусом `422 Unprocessable Entity`, если `deadline < earliest_start + duration_minutes`. |
| <a id="fr-api-03"></a>**FR-API-03** | API Gateway | UC-01, UC-05 | Ответ эндпоинта рекомендаций ДОЛЖЕН содержать `job_id` и список `recommendations` — не больше двух элементов, каждый с полями `recommendation_id`, `target_datacenter`, `recommended_start`, `recommended_end`, `estimated_cost_eur`, `baseline_cost_eur`, `estimated_savings_eur`, `estimated_savings_percent`, `is_fallback` (boolean). `is_fallback = true` ставится, если в расчете элемента (окно или базовая стоимость) использована хотя бы одна оценочная цена. Элемент с `is_fallback = false` — основная рекомендация, целиком по реальным ценам, ее клиент исполняет по умолчанию; элемент с `is_fallback = true` — оценочный вариант. Если основной рекомендации нет, ответ ДОЛЖЕН содержать причину — `no_confirmed_window` (ни одно окно не помещается в известные цены) или `baseline_estimated` (базовое окно задевает часы без цены), а клиент запускает задачу по своему расписанию. **Базовая стоимость** `baseline_cost_eur` — стоимость выполнения той же задачи в ЦОД `preferred_datacenter_id` со старта в `baseline_start`, рассчитанная по тем же ценам и модели PUE, что и рекомендация. `estimated_savings_eur = baseline_cost_eur − estimated_cost_eur`, `estimated_savings_percent = estimated_savings_eur / baseline_cost_eur × 100`. Оценочный вариант ДОЛЖЕН присутствовать, если дедлайн позже последнего часа с известными ценами: окно ищется до дедлайна по реальным ценам там, где они есть, и по оценочным — дальше ([ADR-001](adr/ADR-001-engine-input-data.md)). |
| <a id="fr-api-04"></a>**FR-API-04** | API Gateway | UC-03 | Система ДОЛЖНА предоставлять эндпоинт `GET /api/v1/analytics/savings`, возвращающий агрегированные показатели сэкономленных средств (€) и сокращения выбросов $CO_2$ с группировкой по дням, неделям и месяцам за указанный диапазон дат. |
| <a id="fr-api-05"></a>**FR-API-05** | API Gateway | UC-06 | Система ДОЛЖНА предоставлять административные эндпоинты `GET, POST, PUT /api/v1/datacenters` для управления реестром дата-центров компании. |
| <a id="fr-eng-01"></a>**FR-ENG-01** | Optimization Core | UC-01, UC-02 | Система ДОЛЖНА рассчитывать динамический PUE площадки на каждый час интервала как функцию уличной температуры:<br>• `PUE(T) = base_pue` при T ≤ 15 °C (*Free Cooling*);<br>• `PUE(T) = base_pue + 0.015 × (T − 15)` при T > 15 °C (*Chiller Cooling*). |
| <a id="fr-eng-02"></a>**FR-ENG-02** | Optimization Core | UC-01 | Алгоритм оптимизации ДОЛЖЕН осуществлять поиск окна методом непрерывного скользящего окна (*Non-preemptive Hard Constraint*): дробление задачи на части запрещено. |
| <a id="fr-eng-03"></a>**FR-ENG-03** | Optimization Core | UC-01, UC-02 | Алгоритм ДОЛЖЕН строго гарантировать выполнение условия дедлайна: `recommended_end ≤ deadline`. Запрещается предлагать более дешевое окно, выходящее за рамки дедлайна. |
| <a id="fr-eng-04"></a>**FR-ENG-04** | Optimization Core | UC-02 | Система ДОЛЖНА учитывать накладные расходы на межрегиональную передачу данных (*Egress Cost*) и рекомендовать миграцию в удаленный ЦОД только при соблюдении правила: `savings_eur > data_volume_gb × network_tariff_eur_per_gb`. |
| <a id="fr-eng-05"></a>**FR-ENG-05** | Optimization Core | UC-05 | Если ни одно окно нужной длительности не помещается в часы с известными Day-Ahead ценами (в том числе при отсутствии свежих котировок), система НЕ ДОЛЖНА выдавать основную рекомендацию; вместо нее она ДОЛЖНА сформировать оценочный вариант по медиане цен того же часа суток за 3 предшествующие недели с флагом `is_fallback = true` и указать причину `no_confirmed_window` ([ADR-001](adr/ADR-001-engine-input-data.md)). |
| <a id="fr-etl-01"></a>**FR-ETL-01** | Ingestion Layer | UC-04 | Система ДОЛЖНА выполнять автоматический опрос ENTSO-E API не реже одного раза в сутки в интервале 13:00–14:00 CET для загрузки котировок Day-Ahead на следующие сутки. |
| <a id="fr-etl-02"></a>**FR-ETL-02** | Ingestion Layer | UC-04 | Модуль сбора ДОЛЖЕН выполнять периодическую синхронизацию метеопрогноза Open-Meteo каждые 3 часа на горизонт 16 дней вперед для географических координат всех активных ЦОД. |
| <a id="fr-etl-03"></a>**FR-ETL-03** | Ingestion Layer | UC-04 | Система ДОЛЖНА поддерживать пакетный режим первичной ретроспективной загрузки архива цен и генерации ENTSO-E, а также метеоархива за 3–5 лет для задач EDA и ML. |
| <a id="fr-etl-04"></a>**FR-ETL-04** | Data Quality | UC-04 | Модуль Data Quality Gate ДОЛЖЕН проверять каждую входящую партию цен: полнота интервалов 100%, отсутствие дубликатов таймстемпов, нахождение цен в границах от -500.00 до +4000.00 EUR/MWh. |
| <a id="fr-etl-05"></a>**FR-ETL-05** | Storage Layer | UC-04 | Запись данных в таблицы PostgreSQL ДОЛЖНА выполняться идемпотентно с использованием механизма `ON CONFLICT (primary_keys) DO UPDATE`. |
| <a id="fr-ui-01"></a>**FR-UI-01** | Web Interface | UC-02 | Пользовательский интерфейс ДОЛЖЕН отображать интерактивную цветовую карту энергозон присутствия компании с индикацией текущих биржевых цен. |
| <a id="fr-ui-02"></a>**FR-UI-02** | Web Interface | UC-02 | Веб-портал ДОЛЖЕН содержать форму симулятора задач с возможностью ввода мощности, длительности, дедлайна и наглядным графиком почасового распределения затрат. |
| <a id="fr-ui-03"></a>**FR-UI-03** | Web Interface | UC-03 | Дашборд ДОЛЖЕН отображать динамику сэкономленных средств в валюте евро и процент экономии относительно базовой стоимости `baseline_cost_eur`. |

## 2. Нефункциональные требования (Non-Functional Requirements — NFR)

Все требования содержат измеримые инженерные метрики без субъективных оценок.

### 2.1. Производительность (Performance & Latency)
* <a id="nfr-perf-01"></a>**NFR-PERF-01 (API Latency):** Время отклика REST API на запрос расчета рекомендаций (`POST /api/v1/recommendations`) при горизонте планирования до 48 часов и числе площадок до 5 не должно превышать **200 мс** на 95-м перцентиле (p95) и **350 мс** на 99-м перцентиле (p99) при постоянной нагрузке 50 RPS.
* <a id="nfr-perf-02"></a>**NFR-PERF-02 (ETL Ingestion Throughput):** Процесс парсинга, валидации и вставки суточного пакета спотовых цен ENTSO-E (до 5 энергозон, 480 записей) в базу данных PostgreSQL должен занимать не более **15 секунд**.
* <a id="nfr-perf-03"></a>**NFR-PERF-03 (Web UI Responsiveness):** Время отрисовки ключевых дашбордов и карты тарифов в браузере (First Contentful Paint, FCP) не должно превышать **1.2 секунды** при скорости клиентского соединения от 10 Мбит/с.
* <a id="nfr-perf-04"></a>**NFR-PERF-04 (Database Query Optimization):** Аналитические выборки цен и динамического PUE за скользящее окно 48 часов должны выполняться за время не более **10 миллисекунд** за счет использования составных B-Tree индексов.

### 2.2. Надежность и доступность (Reliability & Availability)
* <a id="nfr-rel-01"></a>**NFR-REL-01 (Service Availability):** Доступность API Gateway и расчетного движка должна составлять не менее **99.9%** (Uptime) в режиме 24/7/365 (суммарный внеплановый простой не более **43 минут в месяц**). *(Перенесено в Release 1.0).*
* <a id="nfr-rel-02"></a>**NFR-REL-02 (Recovery Time Objective — RTO):** При аварийном завершении контейнера время автоматического перезапуска средствами Docker Restart Policy (`unless-stopped`) и возврата в состояние готовности обрабатывать трафик (healthcheck `HTTP 200 /health`) не должно превышать **30 секунд**.
* <a id="nfr-rel-03"></a>**NFR-REL-03 (Graceful Degradation):** При полной недоступности внешних сетевых зависимостей (ENTSO-E, Open-Meteo) сервис не должен прекращать обработку входящих запросов Airflow. Доля успешных ответов (в режиме Fallback) должна составлять **100%**, при этом погрешность расчетной стоимости относительно факта не должна превышать **15%**.

### 2.3. Информационная безопасность (Security & Privacy)
* <a id="nfr-sec-01"></a>**NFR-SEC-01 (Zero Outbound Metadata Leaks):** Во внешнюю сеть (Интернет) категорически запрещена передача любых идентифицирующих данных клиента: идентификаторов задач `job_id`, параметров вычислительного кластера, внутренних сетевых адресов и имен серверов. Объем утечки корпоративных метаданных — **строго 0 байт**.
* <a id="nfr-sec-02"></a>**NFR-SEC-02 (Egress Network Filtering):** Сетевой трафик из Docker-контейнеров во внешнюю сеть должен быть строго ограничен белым списком FQDN-имен (`transparency.entsoe.eu` и `api.open-meteo.com` / `archive-api.open-meteo.com`) исключительно по протоколу HTTPS (порт 443).
* <a id="nfr-sec-03"></a>**NFR-SEC-03 (Authentication & Authorization):** Все входящие HTTP-запросы к API Gateway должны быть авторизованы с использованием статического Bearer API-токена в заголовке `Authorization: Bearer <TOKEN>`. Запросы без токена или с недействительным токеном должны отклоняться со статусом `401 Unauthorized` за время не более **15 мс**.

### 2.4. Сопровождаемость и переносимость (Maintainability & Portability)
* <a id="nfr-maint-01"></a>**NFR-MAINT-01 (Deployment Portability):** Сервис должен полностью разворачиваться из репозитория одной командой `docker compose up -d` на сервере под управлением ОС Linux (Ubuntu 22.04 LTS / Debian 12) или macOS без ручной установки системных зависимостей, кроме Docker Engine 24+ и Docker Compose v2+.
* <a id="nfr-maint-02"></a>**NFR-MAINT-02 (Test Coverage):** Покрытие ядра бизнес-логики (модули расчета PUE, алгоритм скользящего окна, Data Quality Gate) модульными и интеграционными тестами (`pytest`) должно составлять не менее **80%** по метрике line coverage.
* <a id="nfr-maint-03"></a>**NFR-MAINT-03 (Structured Logging):** 100% системных и прикладных логов должны выводиться в стандартный поток `stdout` в формате JSON Lines (JSONL), содержать поля `timestamp` (ISO 8601 UTC), `level` (`INFO/WARNING/ERROR`), `trace_id`, `component` и `execution_time_ms`.

## 4. Архитектурно значимые требования (Architecturally Significant Requirements — ASR)

* <a id="asr-01"></a>**ASR-01: On-Premise VPC изоляция (Zero Outbound Metadata).**  
  *Источники:* `NFR-SEC-01`, `NFR-SEC-02`.  
  *Решение:* Автономный Docker Compose контур, запрет отправки метаданных во внешнюю сеть, сетевой whitelist на исходящие HTTPS-запросы к поставщикам данных.
* <a id="asr-02"></a>**ASR-02: Жесткий предел времени ответа API (p95 $\le 200$ мс при 50 RPS).**  
  *Источники:* `NFR-PERF-01`, `FR-API-01`.  
  *Решение:* FastAPI (асинхронный I/O) + пулы соединений `psycopg`/`asyncpg` + векторизованный расчет скользящего окна в памяти.
* <a id="asr-03"></a>**ASR-03: Эффективное хранение и выборка временных рядов (Timeseries Scale).**  
  *Источники:* `FR-ETL-03`, `DR-01`, `DR-07`.  
  *Решение:* Составные B-Tree индексы по временным полям `(bidding_zone, period_start)`, готовность к секционированию по месяцам.
* <a id="asr-04"></a>**ASR-04: Неделимость вычислительного слота (Non-preemptive Batch Execution).**  
  *Источники:* `FR-ENG-02`, Бизнес-правило неделимости пакетных задач.  
  *Решение:* Алгоритм непрерывного скользящего окна фиксированной длины $N$, линейная алгоритмическая сложность $O(M)$.

## 5. Ограничения (Constraints) и Допущения (Assumptions)

### Ограничения проекта (Constraints)
* **CONST-1 (Сроки):** 1-й семестр — Release 0.5 (декабрь 2026), 2-й семестр — Release 1.0 (май 2027).
* **CONST-2 (Команда):** 5 человек, лимит 6 человеко-часов в неделю на участника (всего 300 чел.-ч на семестр).
* **CONST-3 (Бюджет):** 0 ₽. Использование только бесплатных/открытых API, ПО с открытым исходным кодом и локальных машин.
* **CONST-4 (Архитектура):** Развёртывание строго On-Premise через Docker Compose, без SaaS-зависимостей.
* **CONST-5 (Стек):** Python 3.11 / FastAPI, PostgreSQL 16, React + TypeScript. Смена стека — только через Change Request.
* **CONST-6 (Инструменты):** Все задачи, знания и репозитории ведутся на платформе «Сфера».
* **CONST-7 (Данные клиента):** Реальная инфраструктура ЦОД заказчика недоступна, реестр площадок и поток задач — синтетические.

### Допущения (Assumptions)
* **ASM-1:** Security Token ENTSO-E выдан команде и действует весь семестр (при задержке разработка идет на фикстурах/моках).
* **ASM-2:** ENTSO-E публикует цены Day-Ahead до 14:00 CET ежедневно; Open-Meteo бесплатно отдает прогноз (лимит 10 000 req/day).
* **ASM-3:** Требования стабильны до Release 0.5, изменения вносятся только через Change Request (CR).
* **ASM-4:** Синтетических параметров 3 ЦОД достаточно для демонстрации ценности и прохождения приёмки.
* **ASM-5:** Состав команды и доступность сохраняются до окончания семестра.
* **ASM-6:** Ресурсов ноутбуков команды хватает для запуска полного стека и нагрузочного теста 50 RPS.

## 6. Матрица приоритизации (MoSCoW)

| Приоритет | Требования | Обоснование |
| :--- | :--- | :--- |
| **Must Have (M)**<br>*Критично для MVP* | `FR-API-01`, `FR-API-02`, `FR-API-03`, `FR-ENG-02`, `FR-ENG-03`, `FR-ETL-01`, `FR-ETL-04`, `FR-ETL-05`, `NFR-PERF-01`, `NFR-SEC-01`, `NFR-SEC-02`, `NFR-SEC-03`, `NFR-MAINT-01`, `DR-01`, `DR-05`, `DR-06`, `DR-07` | Минимальный работоспособный скелет сервиса: приём задачи от оркестратора, поиск минимума по цене, сохранение в БД. |
| **Should Have (S)**<br>*Важно для релиза 0.5* | `FR-ENG-01` (Dynamic PUE), `FR-ENG-05` (Fallback Mode), `FR-ETL-02` (Погода Open-Meteo), `FR-API-05` (Реестр ЦОД), `FR-UI-02` (Симулятор Web), `NFR-REL-02` (RTO), `NFR-REL-03` (Degradation), `NFR-PERF-02` (ETL), `NFR-PERF-04` (Индексы), `NFR-MAINT-02` (Тесты $\ge 80\%$), `NFR-MAINT-03` (JSON-логи), `DR-03` (Прогноз погоды) | Обеспечивают точность расчета физического охлаждения ЦОД, отказоустойчивость при сетевых сбоях и удобство работы через UI. |
| **Could Have (C)**<br>*Полезно при наличии ресурсов* | `FR-API-04` (Analytics API), `FR-UI-01` (Карта тарифов), `FR-UI-03` (FinOps Dashboard), `FR-ENG-04` (Egress Cost), `FR-ETL-03` (Backfill архива), `NFR-PERF-03` (FCP UI), `DR-02` (Генерация), `DR-04` (Метеоархив) | Аналитическая и визуальная надстройка над расчетным ядром; повышает демонстрационную ценность на защите. |
| **Won't Have (W)**<br>*Отложено на 2-й семестр (Release 1.0)* | `ML-Forecast 7-day` (прогноз цен на 7 дней вперед на базе ML), Автоматическое управление питанием серверов (IPMI / Redfish), интеграция с Airflow/Kubeflow в боевой сети клиента. | Требуют накопления исторических данных и отдельного контура инфраструктурной интеграции. |
