## Контекст

Схему БД и загрузку данных делает Богдан, API — Александр. API читает данные, которые пишет ETL, и само пишет задачи и рекомендации. Чтобы обе стороны работали независимо и не ломали друг друга, нужно договориться:

* кто в какие таблицы пишет и откуда API читает;
* что API может ожидать от данных: полноту, свежесть, время;
* как записываются задачи и рекомендации;
* как меняется схема, пока нет инструмента миграций.

## Решения

### 1. Схема
* Источник истины схемы — [`infra/db/init.sql`](../../infra/db/init.sql); описание полей и связей — [ERD](../data/ERD.md).
* Схему меняет только Богдан, через PR. Ревьюит потребитель: таблицы, которые читает или пишет API, — Александр.
* `init.sql` можно прогнать повторно на существующей базе, но `CREATE TABLE IF NOT EXISTS` не обновит уже созданные таблицы; порядок изменения схемы описан ниже.

### 2. Кто пишет в какие таблицы
| Таблица | Пишет | Читают |
| :--- | :--- | :--- |
| `entsoe_day_ahead_prices` | только `etl-worker` | API — через представление `v_entsoe_prices_hourly` |
| `open_meteo_forecast` | только `etl-worker` | API |
| `open_meteo_historical_weather` | только `etl-worker` (разовые загрузки) | аналитика; API не читает |
| `datacenters` | сид в `init.sql`; дальше — API через административные эндпоинты ([`FR-API-05`](../REQUIREMENTS.md#fr-api-05)) | `etl-worker`, API |
| `jobs` | только API | API, аналитика |
| `recommendations` | только API | API, аналитика |

Компонент, который не указан как пишущий, таблицу только читает.

### 3. Что API читает
* **Цены** — только из `v_entsoe_prices_hourly`, не из таблицы цен: представление уже приводит ряды к почасовой сетке ([ADR-001](ADR-001-engine-input-data.md)).
* **Оценочные цены** (медиана за 3 недели для оценочного варианта рекомендации) — тоже из `v_entsoe_prices_hourly`, из исходных цен; медиана используется только для оценочного варианта API и не применяется в DQ.
* **Погода** — из `open_meteo_forecast`; исходная строка заменяет оценочную; оценочная не перезаписывает исходную. Допускаются незаполненные разрывы по ADR-003.
* **ЦОД** — из `datacenters`, только `is_active = TRUE`; зона ЦОД — поле `bidding_zone`.

### 4. Что гарантирует ETL
* Все метки времени — UTC.
* Цены по каждой зоне — за сегодня и, после публикации около 13:00 CET, за завтра. ETL проверяет весь запрошенный диапазон; длинные и краевые разрывы остаются пустыми с записью в журнале (ADR-003).
* Прогноз погоды обновляется каждые 3 часа и запрашивается на 16 календарных суток UTC; неполнота фиксируется по ADR-003 по каждому активному ЦОД.
* При развертывании загружается архив цен минимум за 3 недели, иначе медиану для fallback не из чего считать.
* Значения проходят проверку диапазонов в ETL до записи; `CHECK`-ограничений в БД нет ([ERD, п. 4](../data/ERD.md)).

### 5. Как API пишет задачи и рекомендации
* Запрос проверяется в API до записи; некорректный отклоняется с `422` и в БД не попадает ([`DR-06`](../REQUIREMENTS.md#dr-06)).
* Задача и рекомендация записываются **одной транзакцией**: `jobs`, затем `recommendations`. При ошибке расчета или записи транзакция откатывается целиком ([`DR-07`](../REQUIREMENTS.md#dr-07)).
* Повторный запрос с тем же `job_id` обновляет задачу (`INSERT … ON CONFLICT (job_id) DO UPDATE`) и добавляет новую строку в `recommendations`: история расчетов по задаче сохраняется.
* Каждый элемент списка рекомендаций из ответа ([ADR-001](ADR-001-engine-input-data.md)) сохраняется отдельной строкой в `recommendations` в той же транзакции, что и задача. Строки одного запроса имеют одинаковые `job_id` и `calculated_at` (`NOW()` возвращает время начала транзакции).
* Смысл флага однозначный: `is_fallback = FALSE` — основная рекомендация (только по исходным ценам в окне и базовой стоимости), `is_fallback = TRUE` — оценочный вариант. Аналитика экономии и история выданных рекомендаций берут только строки с `is_fallback = FALSE`; отдельное представление для этого не нужно. Если при fallback основной рекомендации нет, у запроса есть только строка с `TRUE`, и в экономию он не попадает.
* Для защиты от двух основных рекомендаций или двух оценочных вариантов в одном запросе планируется ограничение `UNIQUE (job_id, calculated_at, is_fallback)`. В текущем `init.sql` его ещё нет; API должен сохранять не больше одного элемента каждого типа в транзакции.

### 6. Подключение
* Параметры подключения — только через переменные окружения `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, значения — в `.env`.

## Последствия

* API и ETL не зависят друг от друга по коду: общая только схема, и она меняется через PR с ревью потребителя.
* Переход ENTSO-E на другой шаг цен затрагивает только представление, а не SQL в API.
* Пока нет инструмента миграций, изменение **существующей** таблицы не применяется повторным запуском `init.sql`: `CREATE TABLE IF NOT EXISTS` не меняет уже созданную таблицу. Такое изменение оформляется отдельным идемпотентным `ALTER TABLE … ADD COLUMN IF NOT EXISTS …` в `init.sql`, либо локальная база пересоздается.
* Без архива цен за 3 недели fallback не работает; загрузка архива — обязательный шаг развертывания (README, «Локальный запуск»).

## Решения по развертыванию схемы и ролям БД

Предложение Александра от 04.11.2026; вступает в силу после ревью ADR.

* **Инструмент миграций сейчас не вводим.** До Release 0.5 схема небольшая, а `infra/db/init.sql` остаётся источником для новой базы. Для существующей базы каждое изменение таблицы должно содержать явный, идемпотентный SQL-переход (`ALTER TABLE … IF EXISTS/IF NOT EXISTS` и т. п.) с проверкой как на пустой, так и на уже заполненной базе. Повторный запуск `CREATE TABLE IF NOT EXISTS` сам по себе миграцией не является. Перед первым изменением, требующим преобразования или удаления данных, либо перед развертыванием нескольких версий сервиса на общей постоянной базе, решение пересматривается и вводится версионированный инструмент миграций (например, Alembic). Это решение не означает, что текущий `init.sql` уже содержит переходы для всех будущих изменений.
* **Отдельных пользователей БД сейчас не создаём.** В текущем локальном Compose у ETL и будущего API одна роль `ecogrid`; разграничение записи пока обеспечивается контрактом компонентов и ревью PR, а не правами PostgreSQL. Это сознательное ограничение локального MVP. Перед развертыванием у клиента нужно создать отдельные роли и выдать ETL запись только в таблицы цен и погоды, API — в `jobs`, `recommendations` и административно управляемые `datacenters`; чтение — согласно таблице выше. Учетные данные хранятся раздельно в переменных окружения. Без этого шага роли не обеспечивают изоляцию при ошибке или компрометации одного из сервисов.

## Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
| :--- | :--- |
| API читает цены напрямую из `entsoe_day_ahead_prices` | API пришлось бы самому усреднять `PT15M` и выбирать между шагами; эта логика уже есть в представлении |
| Общий Python-модуль доступа к БД для ETL и API | Связывает два сервиса по коду и релизам; общей остается только схема |
| Писать `jobs` и `recommendations` отдельными транзакциями | При сбое между записями в БД остается задача без рекомендации; [`DR-07`](../REQUIREMENTS.md#dr-07) требует отката |

Восстановленные ETL цены помечены is_estimated в v_entsoe_prices_hourly. При их использовании в окне или baseline API возвращает is_fallback = TRUE. Контракт согласуют Александр и Арина (ADR-003).
