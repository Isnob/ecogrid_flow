## Контекст

Расчетное ядро (оптимизатор окна и выбора ЦОД) и API рекомендаций разрабатывают разные люди параллельно. Чтобы контракты K3 и K4 не разошлись, нужно заранее договориться:

* в каком времени и с каким шагом ядро получает ряды;
* на каком горизонте ищется окно, если цены известны только на сутки вперед;
* что делать, если для часа нет прогноза погоды;
* кто собирает цены, погоду и параметры ЦОД в один ряд.

Цены Day-Ahead ENTSO-E публикуются около 13:00 CET на следующие сутки, поэтому в момент запроса известны цены примерно на 11–35 часов вперед. С октября 2025 года часть рядов публикуется с шагом `PT15M`, архив — с шагом `PT60M`. Стоимость часа задачи считается как `мощность × PUE(температура) × цена` ([`FR-ENG-01`](../REQUIREMENTS.md#fr-eng-01)).

## Решения

### 1. Время и шаг
* Все метки времени — UTC (`TIMESTAMPTZ` в БД, ISO 8601 с `Z` в JSON).
* Ядро работает на **почасовой сетке**.
* Источник цен для ядра — представление `v_entsoe_prices_hourly`: 15-минутные цены усредняются до часа, при наличии обоих шагов берется `PT60M`.

### 2. Горизонт расчета, fallback и формат результата
Ядро возвращает, а API отдает **список рекомендаций** — не больше двух элементов одной и той же структуры, которые различаются флагом `is_fallback`:

* **`is_fallback = false` — основная рекомендация.** Считается **только по реальным ценам**: окно целиком помещается в часы с известными ценами и заканчивается не позже `deadline` ([`FR-ENG-03`](../REQUIREMENTS.md#fr-eng-03)). Клиент исполняет ее по умолчанию. В Release 0.5 цены не прогнозируются, поэтому основная рекомендация — всегда факт.
* **`is_fallback = true` — оценочный вариант.** Окно ищется на всем интервале до `deadline`: по реальным ценам там, где они есть, и по оценочным — дальше. Возвращается всегда, когда дедлайн позже последнего часа с известной ценой. Автоматически не исполняется.

| Ситуация | Элементы списка |
| :--- | :--- |
| Дедлайн укладывается в известные цены | один: `is_fallback = false` |
| Дедлайн позже известных цен, окно в известных ценах есть | два: `false` и `true` |
| Ни одно окно не помещается в известные цены (сбой загрузки цен или длинная задача, запрошенная до публикации цен на завтра) — **fallback** ([`FR-ENG-05`](../REQUIREMENTS.md#fr-eng-05)) | один: `is_fallback = true`; **основной рекомендации нет**, в ответе причина `no_confirmed_window` |

* **Поведение клиента.** Airflow исполняет элемент с `is_fallback = false`; если его нет — запускает задачу по своему обычному расписанию (`baseline_start`). Веб-интерфейс показывает оба элемента, оценочный — с пометкой «оценка, цены еще не опубликованы» и советом перезапросить рекомендацию после 13:00 CET.
* **Источник оценочных цен заменяемый.** Оценки готовит API-слой одной функцией «почасовые оценки цен по зоне на интервал». Сейчас это медиана цены того же часа суток за 3 предыдущие недели; в следующем релизе ее заменит ML-прогноз цен без изменения ядра, контракта K3 и ответа API.
* **Горизонт оценок задает источник, а не правило.** Фиксированного предела нет: медиана дает оценку для любого часа, поэтому оценочный вариант ищется до дедлайна, как бы далеко тот ни был; ML-модель будет давать оценки на горизонт своего прогноза. Для часов за горизонтом прогноза погоды действует п. 3.
* **Критерий приемки для fallback** (заменяет сценарий 3 из [требований к приемке](../archive/seminars/seminar_4/readme.md)): если цен на дату расчета нет, а цены за 3 предыдущие недели есть, API отвечает `200 OK`; в списке нет элемента с `is_fallback = false`; есть элемент с `is_fallback = true`, стоимость которого посчитана по медиане; в ответе причина `no_confirmed_window`.

### 3. Погода
* Температура для часов окна берется из `open_meteo_forecast`.
* Прогноз загружается на 16 дней вперед ([`FR-ETL-02`](../REQUIREMENTS.md#fr-etl-02)); в ядро передаются только часы интервала поиска.
* Если прогноза на час нет (в том числе для часов дальше 16 дней), для этого часа используется `PUE = base_pue` ЦОД и пишется предупреждение в лог. Fallback из-за отсутствия погоды не включается: погода только уточняет расчет.

### 4. Сборка рядов
* Цены, погоду и параметры ЦОД собирает в почасовые ряды **API-слой**: одна выборка из `v_entsoe_prices_hourly`, `open_meteo_forecast` и `datacenters` по зонам и ЦОД из запроса.
* Ядро — чистая функция без доступа к БД: на вход получает параметры задачи и ряды по каждому ЦОД, на выход — рекомендацию. Формат входа и выхода фиксируется в контракте K3.

## Последствия

* Ядро тестируется на данных в памяти, без БД и без ENTSO-E; смена схемы таблиц затрагивает только SQL в API-слое.
* Переход ENTSO-E на `PT15M` не затрагивает ядро — его поглощает представление.
* Одна выборка данных на запрос и расчет в памяти укладываются в [`ASR-02`](../REQUIREMENTS.md#asr-02) (p95 ≤ 200 мс): на 3 ЦОД и горизонт до 48 ч это сотни чисел.
* Ограничение горизонта известными ценами может уменьшать экономию для задач с дальним дедлайном: окно не уходит дальше конца суток D+1. Это осознанный компромисс MVP.
* ML-прогноз цен (следующий релиз) подключается заменой одной функции — источника оценочных цен: логика выбора окна, флаг `is_fallback` и список рекомендаций уже работают с оценками.
* Ответ API — список рекомендаций ([`FR-API-03`](../REQUIREMENTS.md#fr-api-03)); он совпадает с выходом ядра и строками таблицы `recommendations`, где элемент с `is_fallback = false` — основная рекомендация ([ADR-002](ADR-002-db-api-contract.md)).
* При fallback сервис не выдает подтвержденной рекомендации; клиент продолжает работать по своему расписанию, а оценка доступна человеку. Это меняет прежнюю редакцию [`FR-ENG-05`](../REQUIREMENTS.md#fr-eng-05), где в fallback выдавалась основная рекомендация по медиане.
* Оценочный вариант на медиане может сильно ошибаться; поэтому он никогда не исполняется автоматически.
* Без фиксированного предела горизонт растет вместе с дедлайном; на 3 ЦОД это тысячи окон даже для дедлайна через месяц, перебор укладывается в миллисекунды.
* Зимой в FI и SE3 температура почти всегда ниже 15 °C, и погода не влияет на стоимость; заметный эффект — летом в DE. Если сроки поджимают, учет погоды можно временно отключить (`PUE = base_pue`) без изменения контракта K3.

## Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
| :--- | :--- |
| Ядро само читает БД (как в черновике CT-04 семинара 7) | Ядро нельзя тестировать без БД; схема таблиц протекает в код оптимизатора |
| Ядро работает в исходном шаге `PT15M` | Сложнее ядро и тесты, а погода все равно почасовая; для MVP точности часа достаточно |
| Основную рекомендацию считать по реальным ценам и оценкам вместе, выбирая самое дешевое окно | Клиент исполнял бы окно, выбранное по догадке; основная рекомендация должна опираться на реальные цены, а оценка — быть отдельным вариантом |
| При fallback выдавать основную рекомендацию по медиане (прежняя редакция `FR-ENG-05`) | В Release 0.5 цены не прогнозируются: основная рекомендация должна быть только фактом, а оценка — отдельным элементом с `is_fallback = true` (замечание ревью) |
| Основная рекомендация на верхнем уровне ответа, оценочная — вложенным блоком `estimated_alternative` | Две разные формы одних и тех же данных; случай «основной рекомендации нет» превращается в набор пустых полей. Список совпадает с выходом ядра и строками БД |
| Подменять основную рекомендацию оценочной, если та дешевле на порог (например, вдвое) | Реальная цена сравнивалась бы с оценкой автоматически; решение о том, ждать ли, остается за пользователем |
| Фиксированный предел горизонта оценок 48 ч | Горизонт зависит от качества источника оценок; при переходе на ML пришлось бы менять правило |
| Fallback при отсутствии прогноза погоды | Погода — фактор второго порядка. `base_pue` — нижняя граница PUE, поэтому стоимость такого часа может быть немного занижена; это фиксируется предупреждением в логе |
