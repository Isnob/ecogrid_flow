## Контекст

Расчетное ядро (оптимизатор окна и выбора ЦОД) и API рекомендаций разрабатывают разные люди параллельно. Чтобы контракты K3 и K4 не разошлись, нужно заранее договориться:

* в каком времени и с каким шагом ядро получает ряды;
* на каком горизонте ищется окно, если цены известны только на сутки вперед;
* что делать, если для часа нет прогноза погоды;
* кто собирает цены, погоду и параметры ЦОД в один ряд.

Цены Day-Ahead ENTSO-E публикуются около 13:00 CET на следующие сутки, поэтому в момент запроса известны цены примерно на 11–35 часов вперед. С октября 2025 года часть рядов публикуется с шагом `PT15M`, архив — с шагом `PT60M`. Стоимость часа задачи считается как `мощность × PUE(температура) × цена` ([`FR-ENG-01`](../REQUIREMENTS.md#fr-eng-01)).

## Решения

### 1. Время и шаг
* Все метки времени — UTC (`TIMESTAMPTZ` в БД, ISO 8601 с `Z` в JSON).
* Ядро работает на **почасовой сетке**.
* Источник цен для ядра — представление `v_entsoe_prices_hourly`: 15-минутные цены усредняются до часа, при наличии обоих шагов берется `PT60M`.

### 2. Горизонт расчета, fallback и оценочный вариант
Ответ содержит **основную рекомендацию** и, когда это имеет смысл, **оценочный вариант**. Клиент по умолчанию исполняет основную: Airflow берет ее, ничего не выбирая; в веб-интерфейсе пользователь видит оба варианта и решает сам.

* **Основная рекомендация — по реальным ценам.** Окно целиком помещается в часы с известными ценами и заканчивается не позже `deadline` ([`FR-ENG-03`](../REQUIREMENTS.md#fr-eng-03)).
* **Fallback для основной рекомендации** ([`FR-ENG-05`](../REQUIREMENTS.md#fr-eng-05)) включается, если ни одно окно нужной длительности не помещается в часы с известными ценами (сбой загрузки цен или длинная задача, запрошенная до публикации цен на завтра). Тогда основная рекомендация считается по оценочным ценам для всего интервала от `earliest_start` до `deadline`, в ответе `is_fallback = true`.
* **Оценочный вариант** считается всегда, когда дедлайн позже последнего часа с известной ценой: окно ищется на всем интервале до `deadline` по реальным ценам там, где они есть, и по оценочным — дальше. Он возвращается в блоке `estimated_alternative` без порогов и фильтров; если дедлайн укладывается в известные цены, блок пустой (`null`). Если оценочный вариант совпал с основным, значит по оценке ждать публикации цен нет смысла. Основную рекомендацию он не подменяет.
* **Источник оценочных цен заменяемый.** Оценки готовит API-слой одной функцией «почасовые оценки цен по зоне на интервал». Сейчас это медиана цены того же часа суток за 3 предыдущие недели; во 2-м семестре ее заменит ML-прогноз цен без изменения ядра, контракта K3 и ответа API.
* **Горизонт оценок задает источник, а не правило.** Фиксированного предела (например, 48 ч) нет: медиана дает оценку для любого часа, ML-модель — на горизонт своего прогноза. Часы за пределами горизонта источника не рассматриваются.

### 3. Погода
* Температура для часов окна берется из `open_meteo_forecast`.
* Если прогноза на час нет, для этого часа используется `PUE = base_pue` ЦОД и пишется предупреждение в лог. Fallback из-за отсутствия погоды не включается: погода только уточняет расчет.

### 4. Сборка рядов
* Цены, погоду и параметры ЦОД собирает в почасовые ряды **API-слой**: одна выборка из `v_entsoe_prices_hourly`, `open_meteo_forecast` и `datacenters` по зонам и ЦОД из запроса.
* Ядро — чистая функция без доступа к БД: на вход получает параметры задачи и ряды по каждому ЦОД, на выход — рекомендацию. Формат входа и выхода фиксируется в контракте K3.

## Последствия

* Ядро тестируется на данных в памяти, без БД и без ENTSO-E; смена схемы таблиц затрагивает только SQL в API-слое.
* Переход ENTSO-E на `PT15M` не затрагивает ядро — его поглощает представление.
* Одна выборка данных на запрос и расчет в памяти укладываются в [`ASR-02`](../REQUIREMENTS.md#asr-02) (p95 ≤ 200 мс): на 3 ЦОД и горизонт до 48 ч это сотни чисел.
* Ограничение горизонта известными ценами может уменьшать экономию для задач с дальним дедлайном: окно не уходит дальше конца суток D+1. Это осознанный компромисс MVP.
* ML-прогноз цен (2-й семестр, R1.0) подключается заменой одной функции — источника оценочных цен: логика выбора окна, флаг `is_fallback` и блок `estimated_alternative` уже работают с оценками.
* Ответ API расширяется необязательным блоком `estimated_alternative` (дополнение к [`FR-API-03`](../REQUIREMENTS.md#fr-api-03)); клиенты, которые его не читают, работают как раньше.
* Оценочный вариант на медиане может сильно ошибаться; поэтому он никогда не исполняется по умолчанию и в интерфейсе подписывается как оценка с советом перезапросить рекомендацию после публикации цен (около 13:00 CET).
* Без фиксированного предела горизонт растет вместе с дедлайном; на 3 ЦОД это тысячи окон даже для дедлайна через месяц, перебор укладывается в миллисекунды.
* Зимой в FI и SE3 температура почти всегда ниже 15 °C, и погода не влияет на стоимость; заметный эффект — летом в DE. Если сроки поджимают, учет погоды можно временно отключить (`PUE = base_pue`) без изменения контракта K3.

## Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
| :--- | :--- |
| Ядро само читает БД (как в черновике CT-04 семинара 7) | Ядро нельзя тестировать без БД; схема таблиц протекает в код оптимизатора |
| Ядро работает в исходном шаге `PT15M` | Сложнее ядро и тесты, а погода все равно почасовая; для MVP точности часа достаточно |
| Основную рекомендацию считать по реальным ценам и оценкам вместе, выбирая самое дешевое окно | Клиент исполнял бы окно, выбранное по догадке; основная рекомендация должна опираться на реальные цены, а оценка — быть отдельным вариантом |
| В fallback использовать реальные цены там, где они есть, и оценки — дальше | Fallback включается, когда реальных цен не хватает даже на одно окно; проще и честнее считать его целиком по оценкам |
| Подменять основную рекомендацию оценочной, если та дешевле на порог (например, вдвое) | Реальная цена сравнивалась бы с оценкой автоматически; решение о том, ждать ли, остается за пользователем |
| Фиксированный предел горизонта оценок 48 ч | Горизонт зависит от качества источника оценок; при переходе на ML пришлось бы менять правило |
| Fallback при отсутствии прогноза погоды | Погода — фактор второго порядка. `base_pue` — нижняя граница PUE, поэтому стоимость такого часа может быть немного занижена; это фиксируется предупреждением в логе |
