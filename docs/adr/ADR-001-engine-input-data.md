# ADR-001. Входные данные расчетного ядра: время, горизонт, погода, сборка рядов

## Контекст

Расчетное ядро (оптимизатор окна и выбора ЦОД, WBS 3.2) и API рекомендаций (WBS 3.4) разрабатывают разные люди параллельно. Чтобы контракты K3 и K4 не разошлись, нужно заранее договориться:

* в каком времени и с каким шагом ядро получает ряды;
* на каком горизонте ищется окно, если цены известны только на сутки вперед;
* что делать, если для часа нет прогноза погоды;
* кто собирает цены, погоду и параметры ЦОД в один ряд.

Цены Day-Ahead ENTSO-E публикуются около 13:00 CET на следующие сутки, поэтому в момент запроса известны цены примерно на 11–35 часов вперед. С октября 2025 года часть рядов публикуется с шагом `PT15M`, архив — с шагом `PT60M`. Стоимость часа задачи считается как `мощность × PUE(температура) × цена` (`FR-ENG-01`).

## Решения

### 1. Время и шаг
* Все метки времени — UTC (`TIMESTAMPTZ` в БД, ISO 8601 с `Z` в JSON).
* Ядро работает на **почасовой сетке**.
* Источник цен для ядра — представление `v_entsoe_prices_hourly`: 15-минутные цены усредняются до часа, при наличии обоих шагов берется `PT60M`.

### 2. Горизонт расчета
* Окно ищется только по часам, на которые цены **уже известны**, и заканчивается не позже `deadline` (`FR-ENG-03`). Часы после последней известной цены не рассматриваются, даже если дедлайн позже.
* Режим fallback (медиана цен за 3 предыдущие недели, `FR-ENG-05`, `BR-05`) включается, только если на ближайшие часы цен **нет совсем** (например, ETL не загрузил цены на завтра). В ответе — `is_fallback = true`.
* Достраивание неизвестных часов медианой и поиск по всему интервалу до дедлайна в MVP **не делается**.

### 3. Погода
* Температура для часов окна берется из `open_meteo_forecast`.
* Если прогноза на час нет, для этого часа используется `PUE = base_pue` ЦОД и пишется предупреждение в лог. Fallback из-за отсутствия погоды не включается: погода только уточняет расчет.

### 4. Сборка рядов
* Цены, погоду и параметры ЦОД собирает в почасовые ряды **API-слой** (WBS 3.4): одна выборка из `v_entsoe_prices_hourly`, `open_meteo_forecast` и `datacenters` по зонам и ЦОД из запроса.
* Ядро — чистая функция без доступа к БД: на вход получает параметры задачи и ряды по каждому ЦОД, на выход — рекомендацию. Формат входа и выхода фиксируется в контракте K3.

## Последствия

* Ядро тестируется на данных в памяти, без БД и без ENTSO-E; смена схемы таблиц затрагивает только SQL в API-слое.
* Переход ENTSO-E на `PT15M` не затрагивает ядро — его поглощает представление.
* Одна выборка данных на запрос и расчет в памяти укладываются в `ASR-02` (p95 ≤ 200 мс): на 3 ЦОД и горизонт до 48 ч это сотни чисел.
* Ограничение горизонта известными ценами может уменьшать экономию для задач с дальним дедлайном: окно не уходит дальше конца суток D+1. Это осознанный компромисс MVP; прогноз цен на 3–7 дней — во 2-м семестре (R1.0).
* Зимой в FI и SE3 температура почти всегда ниже 15 °C, и погода не влияет на стоимость; заметный эффект — летом в DE. Если сроки поджимают, учет погоды можно временно отключить (`PUE = base_pue`) без изменения контракта K3.

## Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
| :--- | :--- |
| Ядро само читает БД (как в черновике CT-04 семинара 7) | Ядро нельзя тестировать без БД; схема таблиц протекает в код оптимизатора |
| Ядро работает в исходном шаге `PT15M` | Сложнее ядро и тесты, а погода все равно почасовая; для MVP точности часа достаточно |
| Достраивать неизвестные часы медианой до дедлайна | Смешивает реальные и оценочные цены в одном окне, усложняет флаг `is_fallback` и проверку экономии |
| Fallback при отсутствии прогноза погоды | Погода — фактор второго порядка. `base_pue` — нижняя граница PUE, поэтому стоимость такого часа может быть немного занижена; это фиксируется предупреждением в логе |
