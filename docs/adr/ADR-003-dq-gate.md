# ADR-003. Восстановление пропусков в DQ Gate

**Статус:** Предложено

**Задача:** ID24_EGF-28

**Ревью:** Богдан; изменения контракта БД/API — Александр
**Связанные решения:** [ADR-001](ADR-001-engine-input-data.md), [ADR-002](ADR-002-db-api-contract.md)

## Контекст

DQ Gate проверяет цены и погоду до записи в БД. Некорректные строки должны сохраняться в журнале, корректные — в рабочих таблицах. Возникающие пропуски требуется по возможности заполнять, сохраняя различие между исходными и оценочными данными.

## Решение

1. **Проверки и журнал.** Цены принимаются в диапазоне −500…4000 EUR/MWh, температура — −50…50 °C, влажность — 0…100%, включая границы. Отсутствующие обязательные и неконечные числовые значения отклоняются. Таблица `etl_dq_log` хранит исходную нормализованную строку, причину, источник, зону/ЦОД, идентификатор партии и время. В ней также фиксируются результаты восстановления. Журнал и данные записываются в одной транзакции.

2. **Полнота цен.** Для каждой представленной в ответе зоны, даты и разрешения проверяется сетка рыночных суток Europe/Brussels: обычно 24 часовых или 96 четвертьчасовых интервалов; при переводе часов — 23/25 или 92/100. Полностью отсутствующие в ответе сутки не создаются: цены могут быть ещё не опубликованы.

3. **Восстановление цен.** Сначала используется уже сохранённая корректная реальная цена того же интервала. Иначе берётся медиана той же зоны, разрешения и времени суток UTC за предыдущие 21 сутки. Конец окна истории — более раннее из начала суток поставки и момента расчёта. Используются только корректные реальные строки из БД и текущей партии. Достаточно одного наблюдения; их количество фиксируется в журнале. При отсутствии истории пропуск остаётся и журналируется, остальные строки сохраняются.

4. **Восстановление погоды.** В пределах диапазона временных меток ответа используется ближайшая корректная точка не дальше одного часа; при равном расстоянии — более ранняя. Восстановленные точки не используются для последующего заполнения. Без подходящего соседа пропуск остаётся с записью в журнале. Горизонт прогноза не продлевается.

5. **Маркировка и замена.** Поле `imputation_method` в таблицах цен и прогноза: `NULL` — исходные данные, `median_21d` — восстановленная цена, `nearest_hour` — восстановленная погода. Реальные значения заменяют оценки; оценки не перезаписывают реальные значения. Восстановленные цены не входят в историю для медианы.

6. **Использование цен.** Представление `v_entsoe_prices_hourly` возвращает только полные часы. Поле `is_estimated` равно `TRUE`, если хотя бы один интервал часа восстановлен. При конкурирующих разрешениях предпочтение отдаётся реальному ряду, затем PT60M. Планировщик продолжает запросы до полного покрытия завтрашних суток реальными ценами. Для будущего API предлагается использовать оценочные цены только в оценочном варианте рекомендации (`is_fallback = TRUE`), исключая их из основной рекомендации и истории для медианы. Реализация API не входит в эту задачу.

## Последствия и границы

- Полнота данных не означает, что все значения опубликованы источником; потребитель должен учитывать признак оценки.
- Правила проверки и восстановления находятся в `run_prices.py` и `run_weather.py`; DDL журнала, полей маркировки и представления — в `infra/db/init.sql`.
- Проверяются строки, полученные от существующих загрузчиков. Изменение парсеров внешних ответов в задачу не входит.
- Решение уточняет гарантию безусловной полноты суток из ADR-002: если нет истории для восстановления, допускается неполный ряд с записью в журнале. Это уточнение и правила потребления оценочных цен требуют согласования при ревью.
- Перед запуском обновлённого ETL на существующей БД необходимо после ревью применить обновлённый `init.sql`: перезапуск контейнера сам по себе не обновляет схему существующего тома. Скрипт содержит идемпотентные `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`.
