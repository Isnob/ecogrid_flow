# Семинар 2. Организация Agile-процесса команды

**Цель:** перевести идею проекта из общей постановки в управляемый набор работ и настроить единый процесс, по которому команда будет работать весь семестр.  

---

## Методологический выбор, правила процесса и первоначальный Backlog

### 1. Сравнение Waterfall, Scrum и Kanban применительно к проекту EcoGrid Flow

| Критерий | Waterfall (Каскадная модель) | Scrum (Спринты и церемонии) | Kanban (Управление потоком) |
| :--- | :--- | :--- | :--- |
| **Планирование и требования** | Фиксируются на 100% в начале проекта; изменения через сложный Change Management. | Итеративное планирование на фиксированный отрезок (1–2 недели). Требования внутри спринта «замораживаются». | Непрерывный поток: требования приоритизируются в бэклоге и берутся в работу по мере освобождения ресурсов. |
| **Применимость к студенческому графику (Part-time)** | Не применим: в академическом проекте невозможно составить исчерпывающее ТЗ на 9 месяцев вперед. | Плохо применим: фиксированная емкость (Capacity) постоянно срывается учебой, парами, дедлайнами по другим предметам и работой. | **Идеально применим:** задачи двигаются асинхронно; пропуск одного дня не ломает спринт всей команды. |
| **Учет неоднородности команды (Junior / Middle)** | Не учитывает: задержка на этапе аналитики блокирует весь цикл разработки. | Создает риски: если джуниор не успевает закрыть Story к концу спринта, весь Sprint Goal проваливается. | **Отлично сглаживает:** старшие помогают младшим разблокировать задачи через вытягивание (Pull system) и фокус на завершении. |
| **Специфика Data Engineering & R&D** | Не применим: исследовательские задачи (EDA, парсинг нестабильных API, подбор признаков ML) непредсказуемы. | Затруднен: тяжело точно оценить в Story Points исследовательский спайк (Spike) по очистке грязных данных. | **Естественная среда:** R&D-задачи проходят исследовательский этап (Upstream) без искусственной привязки к таймбоксам. |
| **Церемониальный оверхед** | Минимальный, но жесткий документооборот. | Высокий: ежедневные дейли (15 мин), груминги, демо, ретроспективы (тяжело собирать студентов синхронно). | **Минимальный:** фокус на визуализации доски и асинхронных апдейтах; созвон только по необходимости разблокировки. |

### 2. Выбор основного подхода и аргументация

Команда выбрала **Kanban** как основной методологический подход к разработке EcoGrid Flow.

#### Ключевые аргументы выбора:
1. **Неравномерная и плавающая загрузка студентов (Part-Time / Third-Time режим):**  
   У команды нет фиксированных 40 часов в неделю. Из-за пар, текущих заданий по другим предметам и работы недельная доступность участников постоянно колеблется. В Scrum это приводило бы к постоянному срыву обязательств спринта (Sprint Commitment) и превращало метрику Velocity в фикцию. Kanban устраняет стресс искусственных дедлайнов спринта, обеспечивая равномерное движение задач.
2. **Разрыв в компетенциях участников (Seniority gap):**  
   В команде есть как опытные разработчики (бэкенд, фронтенд), так и участники, впервые осваивающие стек (QA-автотесты, Data Quality, физика PUE). При жестких спринтах зависимость задач друг от друга приводит к простоям. В Kanban действует принцип *«Закончи начатое, прежде чем брать новое» (Stop starting, start finishing)* — более опытные участники могут подключиться к проверке или парному программированию, не дожидаясь окончания итерации.
3. **Высокая степень исследовательской неопределенности (R&D в Data Engineering):**  
   Работа с открытыми источниками (ENTSO-E API, Open-Meteo) сопряжена с непредвиденными сложностями: смена схем XML-ответов, пропуски таймзон, сбои серверов бирж. Такие задачи сложно оценить детерминированно в часах. Kanban позволяет изолировать исследовательские задачи в Upstream-потоке.
4. **Гибкость требований (Scope Flexibility):**  
   По мере получения обратной связи от преподавателя архитектурные решения могут уточняться. В Kanban переприоритизация бэклога в колонке `To Do` происходит мгновенно и безболезненно.

> [!IMPORTANT]
> **Управление риском прокрастинации (критическое замечание):**  
> Главная опасность чистого Kanban в студенческих командах — размывание сроков (закон Паркинсона). Чтобы задачи не зависали в статусе `In Progress` на недели, команда вводит **WIP-лимиты** (ограничение одновременно выполняемых задач) и привязывает ключевые контрольные точки к семестровым релизам проекта (Release 50% в декабре).

### 4. Статусы рабочей доски

Для отражения реального жизненного цикла задачи в проекте приняты 6 статусов доски:

| Статус | Значение статуса | Кто переводит в статус |
| :--- | :--- | :--- |
| **Backlog** | Идея или потребность зафиксирована, описана на уровне требований, но еще не взята в работу. | Team Lead / Product Owner (Богдан) |
| **To Do** | Задача полностью готова к разработке (сформулированы критерии приемки), имеет приоритет и назначена исполнителю. | Исполнитель (по согласованию с Team Lead) |
| **In Progress** | Исполнитель прямо сейчас работает над кодом / аналитикой / артефактом задачи. | Исполнитель (при взятии задачи в работу) |
| **Review** | Работа выполнена, создан Merge Request (MR) в Git-репозитории. Проводится взаимное Code Review или проверка артефакта. | Исполнитель (после создания MR) |
| **Testing** | Код залит в тестовую ветку, QA-инженер проверяет функциональность, интеграцию и прохождение автотестов. | QA Engineer (Гриша) |
| **Done** | Результат соответствует Definition of Done, протестирован, влит в ветку `main` / `develop` и закрыт. | Team Lead (Богдан) / QA (Гриша) |

### 5. Правила изменения статусов и WIP-лимиты

#### Правила переходов:
1. **Переход `Backlog → To Do`:** Задача декомпозирована, понятна цель, определен конкретный Deliverable (файл, скрипт, эндпоинт).
2. **Переход `To Do → In Progress`:** 
   * Исполнитель переводит задачу самостоятельно;
   * На задаче **обязан** стоять один ответственный исполнитель;
   * Создается отдельная ветка в Git по стандарту: `feature/TSK-XX-short-name`.
3. **Переход `In Progress → Review`:**
   * Код загружен в репозиторий, открыт Merge Request (MR);
   * В описании MR указан номер задачи из трекера (например, `Closes TSK-03`);
   * Локально код компилируется/запускается без ошибок.
4. **Переход `Review → Testing`:**
   * Получено минимум 1 одобрение (Approve) от назначенного ревьюера;
   * Замечания устранены.
5. **Переход `Testing → Done`:**
   * Пройдены все критерии Definition of Done;
   * Ветка влита в основную ветку репозитория.
6. **Возврат на доработку:** если на этапе `Review` или `Testing` найден критический баг/несоответствие, задача возвращается в `In Progress` с обязательным комментарием о причине возврата.

#### WIP-лимиты (Work In Progress limits):
* **Колонка `In Progress`:** максимум **1 задача на одного человека** (суммарно не более 5 задач на команду). Запрещено брать вторую задачу, пока не завершена или не передана на ревью текущая.
* **Колонка `Review`:** не более **3 задач одновременно** на всю команду. Если колонка переполнена, разработчики обязаны остановиться и провести ревью коллегам, прежде чем брать новые задачи.

### 6. Первичная проверка результата перед Done

Проверка перед финальным закрытием задачи разделяется по типу работ:
* **Для программного кода (Backend, ETL, Frontend):**
  * Первичное Code Review проводит **Александр Зейферт** (архитектура, чистота кода, безопасность, соблюдение контрактов API).
  * Фронтенд-компоненты взаимно верифицируют **Богдан Леонов** (соответствие требованиям интерфейса) и **Александр** (интеграция с API).
* **Для аналитики данных, датасетов и PUE-моделей:**
  * Проверку математической корректности и чистоты данных проводят **Богдан Леонов** совместно с **Ариной Антоновой**.
* **Для функционального и интеграционного тестирования:**
  * Тестирование проводит **Григорий Витрик** (проверка выполнения тестов, прогона через тестовые данные, отсутствия регрессий).
* **Финальный перевод в Done:** осуществляет **Team Lead (Богдан Леонов)** после подтверждения от QA и ревьюера.

### 7. Минимальный Definition of Done (DoD)

Обычная проектная задача считается завершенной (**Done**) только при соблюдении следующих критериев:

1. **Код в репозитории:** Весь написанный исходный код загружен в репозиторий проекта в ветку соответствующей функциональности.
2. **Code Review:** Открыт Merge Request, получен как минимум 1 аппрув от коллеги, ветка успешно смерджена без конфликтов.
3. **Работоспособность и тесты:** Код выполняется без ошибок, базовые проверки (`pytest` / линтеры / сборка фронтенда) проходят успешно.
4. **Документирование:** Если задача меняет API или архитектуру данных, изменения зафиксированы в документации (docstrings, Swagger, Markdown-спецификации).
5. **Работоспособность в Docker:** Если задача касается сервисов ядра, изменение проверено на запуск в окружении Docker Compose.
6. **Обновление в трекере:** Карточка задачи в «Сфера.Задачи» переведена в статус `Done` с прикрепленной ссылкой на коммит/MR.

### 8. Ритм командных синхронизаций и правила обновления задач в «Сфере»

Поскольку все участники команды учатся в одной академической группе (ИД24), выбран **очный формат синхронизаций в учебные дни:**

* **Очные стендап-синхронизации (3 раза в неделю на парах / в перерывах, по 20–30 минут):**
  * Разбор текущей ситуации по канбан-доске (что сделано, что сейчас в `In Progress`);
  * Выявление блокеров и взаимная помощь (разбор сложных технических моментов, помощь джуниорам со стороны старших);
  * Оперативное распределение следующих задач из колонки `To Do`.
* **Асинхронные коммуникации в командном чате (по мере необходимости):**
  * Публикация ссылок на созданные Merge Requests (MR) для ускорения Code Review;
  * Экстренное оповещение о блокерах (упал внешний API, сетевые ошибки, проблемы с токенами).
* **Правило обновления задач в «Сфере»:**
  * Карточка переводится в статус **в тот же день**, когда фактически начата или передана работа (запрещено «пакетно» закрывать все задачи в конце месяца перед контрольной точкой);
  * Если исполнитель заблокирован внешней проблемой (упал API, нет ключа, зависла зависимость), в карточке задачи ставится тег/статус **Blocker** и пишется комментарий о причине простоя.
