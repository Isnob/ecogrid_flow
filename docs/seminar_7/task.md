Семинар 7. Тема: масштабирование управления разработкой ПО.

Цель: смоделировать рост проекта от одной учебной команды к нескольким командам, совместно развивающим data-платформу.

Что необходимо сделать

1. Выделить основные функциональные области программного продукта. Разделить разрабатываемую систему на 3–4 области в зависимости от ее назначения и архитектуры.
2. Сформировать команды разработки и распределить обязанности. Определить количество команд, их состав и закрепленные функциональные области. Назначить ответственных за разработку отдельных компонентов, их тестирование и подготовку технической документации. Установить границы ответственности каждой команды, чтобы исключить дублирование работ.
3. Определить общие программные компоненты и согласовать форматы обмена данными. Выявить компоненты, используемые несколькими командами: базы данных, программные интерфейсы, библиотеки, механизмы аутентификации и средства журналирования. Согласовать структуру передаваемых данных, типы полей, форматы запросов и ответов, правила обработки ошибок. Зафиксировать технические соглашения в общей документации проекта.
4. Определить технические зависимости между командами. Установить, какие программные компоненты необходимы другим командам для выполнения их задач. Определить последовательность разработки взаимосвязанных компонентов, порядок предоставления программных интерфейсов и условия начала интеграции. Выделить зависимости, способные повлиять на сроки выполнения проекта.
5. Организовать взаимодействие и координацию команд. Назначить ответственных за согласование архитектурных и технических решений, интеграцию компонентов и контроль выполнения задач. Установить порядок проведения совместных рабочих встреч, согласования изменений и разрешения технических противоречий. Определить единое средство учета задач и фиксации результатов разработки.
6. Установить единые критерии готовности программных компонентов и правила интеграции. Разработать общие требования, при выполнении которых задача считается завершенной: программный код реализован, проверен, протестирован, размещен в общем репозитории и сопровождается необходимой документацией. Определить правила работы с ветками Git, проверки изменений, объединения программного кода и проведения интеграционного тестирования. Установить порядок устранения ошибок, обнаруженных при совместной работе компонентов.
7. Разработать схему организационно-технического взаимодействия команд. Построить диаграмму, отражающую состав команд, закрепленные за ними программные компоненты, зоны ответственности и основные зависимости. Отдельно показать направления обмена данными между компонентами системы и взаимодействие команд при разработке и интеграции.

Артефакты по итогам семинара:

| Артефакт | Что должно быть показано |
| :--- | :--- |
| Схема распределения команд и ответственности | Команды и зоны ответственности. |
| Карта межкомандных зависимостей | Технические и организационные зависимости. |
| Единые правила совместной разработки | Общие контракты, критерии готовности задачи и интеграция. |

Контроль:

1. Команды разделены по устойчивым зонам ответственности.
2. Согласованные требования к структуре и общие компоненты явно выделены.
3. Есть владелец межкомандных зависимостей.

Что сдает команда: Схема масштабирования + карта зависимостей + правила интеграции.

! Текстовый отчет без проектного артефакта не засчитывается. Результат должен быть зафиксирован в «Сфере» и/или репозитории: задача, схема, код, тесты, данные, метрики, логи, MR или релиз.
