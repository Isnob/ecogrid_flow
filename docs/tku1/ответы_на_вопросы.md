# Ответы на вопросы к промежуточной защите (ТКУ1)

Вопросы — из раздела 2 [инструкции](ТКУ1_инструкция.pdf). У каждого ответа указано, кто отвечает в первую очередь. Инструкция предупреждает, что вопрос могут задать любому участнику, поэтому знать главное нужно всем. Ответ должен опираться на наш проект, а не только на определение термина, поэтому для каждого ответа указано, где лежит подтверждение.

## Продукт и данные

**1. Какую конкретную проблему решает ваш продукт и кто его пользователь?** — *Богдан*
Компании со своими дата-центрами запускают тяжёлые задачи (ночные ETL-пайплайны, обучение моделей, бэкапы) по cron в фиксированный час и всегда в одном дата-центре. Цена электроэнергии на бирже за сутки меняется в разы и различается между странами, а от погоды зависит расход на охлаждение, поэтому компания переплачивает. EcoGrid Flow подсказывает, когда и в каком дата-центре запустить задачу дешевле всего, не сорвав дедлайн. Пользователи: дата- и ML-инженеры, которые вызывают сервис из Airflow, и финансовый директор, который смотрит экономию. *Где:* семинар 1, п. 5–6.

**2. Почему для этого нужны обработка и хранение данных?** — *Богдан*
Рекомендацию нельзя посчитать без данных, которые меняются каждый день: цен на завтра по трём зонам и прогноза погоды у дата-центров. Хранить данные нужно по четырём причинам: (1) запасной режим считает по медиане цен за те же дни трёх прошлых недель, для этого нужна история; (2) архив за 3 года нужен для проверки экономии на истории (цель GOAL-2) и для ML-прогноза во 2-м семестре; (3) задачи и рекомендации сохраняются, чтобы показать экономию по каждой задаче; (4) данные проходят проверку качества до записи, и в базу попадают только проверенные. *Где:* семинар 5, п. 1.3; семинар 4, раздел 4.

**3. Какие источники данных используются, кто их владельцы и как вы получаете доступ?** — *Арина*
- **ENTSO-E Transparency Platform** — цены Day-Ahead. Владелец — ENTSO-E и национальные операторы сетей. Доступ через REST API по HTTPS, ответ в XML, нужен бесплатный Security Token после регистрации.
- **Open-Meteo** — прогноз и архив погоды. Владелец — Open-Meteo. Открытый REST API, JSON, без ключа.
- **Справочник дата-центров** — владелец клиент (инфраструктурная служба), доступ через Admin API.
- **Параметры задачи** — приходят от Airflow клиента запросом `POST /api/v1/recommendations`.

*Где:* семинар 3, п. 5 (каталог источников); `docs/data ingestion/data sources.md`.

**4. Чем отличаются существующий (AS-IS) и целевой (TO-BE) процессы?** — *Арина*
AS-IS: задача стартует по cron в фиксированный час, всегда в «домашнем» дата-центре, цена и погода не учитываются, перерасход виден только в месячном счёте. TO-BE: Airflow перед запуском спрашивает API, сервис выбирает самое дешёвое окно до дедлайна и дата-центр из трёх с учётом охлаждения по прогнозу погоды, а стоимость и экономия видны по каждой задаче. *Где:* семинар 3, п. 3.

**5. Что является результатом работы системы?** — *Богдан или Александр*
Основной результат — **REST API**: на запрос с параметрами задачи он возвращает JSON с рекомендацией (время старта и конца, дата-центр, стоимость, базовая стоимость, экономия, флаг запасного режима). Второй результат — **веб-интерфейс** (симулятор задачи). Все рекомендации сохраняются в таблице `recommendations`, по ней потом считается экономия. *Где:* семинар 4, FR-API-01…03.

## Требования и качество данных

**6. Какие функциональные требования основные и как они связаны с пользовательскими сценариями?** — *Григорий*
Основные: `FR-API-01…03` — эндпоинт рекомендаций и формат ответа (сценарий UC-01: запрос из Airflow); `FR-ENG-02`, `FR-ENG-03` — непрерывное окно и соблюдение дедлайна (UC-01, UC-02); `FR-ETL-01`, `FR-ETL-04` — загрузка цен и проверка качества (UC-04: фоновая загрузка); `FR-ENG-05` — запасной режим (UC-05: биржа недоступна). У каждого требования в спецификации указан сценарий. Связь требований с задачами в «Сфере» и ветками — в матрице трассируемости. *Где:* семинар 4, разделы 1–2 и п. 8.2.

**7. Чем FR отличаются от NFR и от требований к данным?** — *Григорий*
- **FR** — что система делает: «выдаёт рекомендацию через `POST /api/v1/recommendations`» (`FR-API-01`).
- **NFR** — насколько хорошо: «ответ API p95 ≤ 200 мс» (`NFR-PERF-01`), «наружу только два адреса» (`NFR-SEC-02`).
- **DR** — какие данные и какого качества: «цены — 24 или 96 значений в сутки на зону, `numeric(8,2)`, хранение 5 лет» (`DR-01`).

Всего 38 требований: 18 FR, 13 NFR, 7 DR. *Где:* семинар 4.

**8. Какие ограничения на формат, схему, объём, частоту и срок хранения данных вы зафиксировали?** — *Григорий или Арина*
На примере цен (`DR-01`): загрузка раз в сутки в 13–14 CET и разовая загрузка архива за 3 года; объём ~105–175 тыс. строк в год; поля `text`, `timestamptz` (UTC), `numeric(8,2)`; таблица в PostgreSQL с партициями по месяцам; хранение 5 лет. Прогноз погоды (`DR-03`) обновляется каждые 3 часа и хранится 3 месяца, архив погоды (`DR-04`) хранится бессрочно, задачи (`DR-06`) — 1 год, рекомендации (`DR-07`) — 3 года. *Где:* семинар 4, раздел 4.

**9. Как определяется качество данных: полнота, корректность, дублирование, актуальность?** — *Григорий*
На примере цен:
- **Полнота** — 100%: за сутки 24 значения при шаге 60 минут или 96 при шаге 15 минут на каждую зону.
- **Корректность** — цена от −500 до 4000 EUR/MWh, валюта EUR.
- **Дубли** — без повторов времени; ключ (зона, начало интервала, шаг), запись через `INSERT … ON CONFLICT DO UPDATE`, поэтому повторная загрузка не создаёт дублей.
- **Актуальность** — цены на завтра есть до 14:30 CET, иначе включается запасной режим.

Для прогноза погоды: не меньше 99% точек, обновлён не более 3,5 часа назад, температура от −50 до +50 °C. *Где:* семинар 4, раздел 4, `FR-ETL-04`, `FR-ETL-05`.

**10. Какой критерий приёмки можно проверить на реальном или тестовом наборе?** — *Григорий*
Сценарий 4: в партию цен для DE-LU подкладываем значение 9999 €/МВт·ч. Строка не попадает в таблицу `entsoe_day_ahead_prices`, в журнал пишется ошибка `DQ_OUT_OF_BOUNDS_PRICE`, загрузка не останавливается. Это критерий контрольной точки 23.10, проверяется автотестом на фикстуре. Второй пример (сценарий 2): если задача не успевает до дедлайна, API отвечает `422`. *Где:* семинар 4, раздел 5; семинар 5, п. 4.2.

**11. Как приоритизируются требования и что войдёт в Release 0.5?** — *Богдан*
Приоритеты расставлены по MoSCoW: Must 17, Should 13, Could 8, плюс отложенные Won't. В Release 0.5 входят все Must, 12 из 13 Should и архив цен и погоды за 3 года. Карта энергозон — первая на вылет при отставании. Во 2-й семестр уходят ML-прогноз цен, интеграция с Airflow, аналитический API и дашборд экономии. *Где:* семинар 4, раздел 6; семинар 5, п. 2.1.

## Организация разработки

**12. Почему выбран Kanban?** — *Максим*
Загрузка у студентов неравномерная: пары, контрольные, работа. Спринты с фиксированными обязательствами постоянно срывались бы. Kanban позволяет брать задачи по мере сил, держать лимит незавершённой работы (не больше одной задачи в работе на человека) и не тратить время на церемонии. Контроль — через контрольные точки раз в две недели. *Где:* семинар 2, п. 1–2, 5.

**13. Как организован бэклог и как задачи связаны с требованиями и результатами?** — *Максим*
В «Сфера.Задачи» бэклог устроен как Epic → Feature → Task. 5 эпиков повторяют части системы: загрузка данных, хранение, ядро, бэкенд, веб. Пример: Epic `ID24_EGF-12` (хранение) → Feature `ID24_EGF-15` (инфраструктура БД) → Task `ID24_EGF-16` (PostgreSQL в Docker). Задачи привязаны к пакетам WBS, а связь «требование → задача → ветка → артефакт» записана в матрице трассируемости. *Где:* доска «Сфера.Задачи»; семинар 4, п. 8.2; семинар 5, п. 3.

**14. Как распределены роли и обязанности?** — *Богдан*
Богдан — Team Lead, Product Owner, Data Engineer (бэклог, требования, загрузка цен ENTSO-E). Александр — Backend и DevOps (API на FastAPI, PostgreSQL, Docker, CI). Арина — Data Analyst и ML (анализ данных, модель PUE, оптимизатор, погода). Максим — Frontend (веб-портал и симулятор). Григорий — QA (качество данных, тесты, приёмка). У каждого результата ровно один ответственный — матрица RACI. *Где:* семинар 1, п. 3; семинар 5, п. 5.

**15. Какие правила Git, Merge Request, ревью и Definition of Done?** — *Александр*
Ветка создаётся от `develop` по шаблону `feature/ID24_EGF-N-…` (для инфраструктуры `infra/…`, для документации `docs/…`). Затем Merge Request с номером задачи и минимум одним одобрением: код смотрит Александр, проверку функций делает Григорий. После этого ветка вливается в `develop`, в `master` — только на релизе. Definition of Done: код в репозитории, ревью пройдено, тесты и линтеры проходят, документация обновлена, сервис запускается в Docker, задача в «Сфере» закрыта со ссылкой на MR. *Где:* семинар 2, п. 5–7; семинар 7, п. 6.

**16. Что включает устав проекта и чем он отличается от паспорта и спецификации?** — *Богдан*
- **Паспорт** (семинар 1) — короткое описание идеи: проблема, пользователи, команда, границы.
- **Устав** (семинар 5) — управленческий документ: зачем проект (обоснование, цели по SMART), в каких рамках (границы, ограничения, допущения), кто участвует (стейкхолдеры, роли), что получится в итоге и как утверждается.

Если коротко: паспорт — «что за проект», устав — «как управляем», спецификация — «что строим».

**17. Как WBS и дорожная карта показывают путь к Release 0.5?** — *Александр*
WBS делит всю работу на 35 пакетов по результатам, всего 255 человеко-часов в пяти направлениях. У каждого пакета один владелец и оценка. Дорожная карта ставит пакеты на контрольные точки раз в две недели (23.10, 06.11, 20.11, 04.12, 11.12, релиз 18.12), у каждой точки проверяемые критерии выхода. Критический путь: схема БД → загрузчик цен → оптимизатор → API → стек в Docker → приёмочные тесты → релиз. Последняя неделя оставлена резервом. *Где:* семинар 5, п. 3–4.

**18. Какие риски наиболее существенны и кто отвечает за их обработку?** — *Максим*
Найдено 25 рисков, 6 связаны с данными. Критических три: загрузка данных на ноутбуках не проработает 14 дней без сбоев (RISK-22, Максим); сессия у всей команды в одни недели (RISK-2, Богдан); ошибки со временем и переходом на зимнее время сорвут дедлайн (RISK-11, Арина). У каждого риска есть владелец, стратегия и ранний сигнал. Для серьёзных рисков заведено 12 задач на снижение. *Где:* семинар 6; запасной слайд П2.

**19. Что будет, если источник станет недоступен или изменит схему?** — *Арина или Григорий*
Если свежих цен нет до 14:30 CET, включается запасной режим: расчёт по медиане цен за те же дни трёх прошлых недель, в ответе `is_fallback = true` и предупреждение. Загрузчик повторяет запрос и догружает пропущенные сутки. На случай отзыва токена есть второй токен ENTSO-E (RT-01). Если поменялся формат ответа, загрузчик выдаёт понятную ошибку, партия не пишется в базу, а изменение ловят тесты на сохранённых настоящих ответах API (RT-08). *Где:* семинар 4, UC-05 и сценарий 3; семинар 6, RISK-14, RISK-19.

## Архитектура

**20. Какие этапы содержит конвейер обработки и зачем нужен каждый?** — *Александр*
1. **Источник** — ENTSO-E и Open-Meteo.
2. **Загрузка** — ETL-воркер по расписанию, повтор при сбое.
3. **Проверка качества** — DQ Gate: полнота, дубли, допустимый диапазон.
4. **Преобразование** — UTC, единый шаг, расчёт PUE по температуре.
5. **Хранение** — PostgreSQL с партициями, запись без дублей.
6. **Выдача** — REST API и веб: расчёт окна и дата-центра под дедлайн.

*Где:* слайд 5.

**21. На каком этапе проверяется корректность данных и что происходит с ошибочными записями?** — *Григорий*
В DQ Gate сразу после загрузки, до записи в базу. Ошибочная строка в таблицу не попадает, причина записывается в журнал с кодом (например, `DQ_OUT_OF_BOUNDS_PRICE`), загрузка продолжается. Если сутки неполные, загрузчик повторяет запрос, а при нехватке данных работает запасной режим. Входящие запросы к API тоже проверяются: неверные поля или недостижимый дедлайн дают ответ `422`. *Где:* семинар 4, `FR-ETL-04`, `FR-API-02`, сценарий 4.

**22. Почему выбран PostgreSQL?** — *Александр*
Данные небольшие и структурированные: ~0,1–0,2 млн строк цен в год, сотни строк погоды в сутки. Реляционной базы хватает с запасом, Big Data не нужен. Партиции по месяцам ускоряют выборки по времени, `ON CONFLICT` даёт запись без дублей, транзакции защищают целостность. PostgreSQL бесплатный и запускается в Docker внутри сети клиента. *Где:* семинар 4, ASR-03; семинар 3, п. 6.2.

**23. Как компоненты обмениваются данными и как фиксируются интерфейсы и форматы?** — *Александр*
Загрузчик пишет проверенные данные в таблицы PostgreSQL. Ядро читает их из базы, API вызывает ядро, веб и Airflow вызывают API по REST/JSON с Bearer-токеном. Интерфейсы записаны как контракты CT-01…CT-07: структура таблиц, функция ядра, REST API (OpenAPI), формат журналов, единый формат ошибок с кодом. У контрактов есть версии, менять их можно только с согласия тех, кто ими пользуется. *Где:* семинар 7, п. 3; описание полей `PreColumns.md`.

**24. Что показывают C4 Context, C4 Container и схема потока данных? Чем они отличаются?** — *Александр*
- **C4 Context** — система целиком как «чёрный ящик»: пользователи и внешние системы вокруг неё (запасной слайд П1, семинар 3).
- **C4 Container** — что внутри системы: воркер загрузки, база, API с ядром, веб — и как они связаны (слайд 5).
- **Поток данных** — через какие этапы данные проходят от источника до результата (слайд 5, верхняя часть).

Context и Container отвечают на вопрос «из чего состоит», поток данных — «что происходит с данными».

**25. Почему выбранный стек соответствует объёмам и задачам?** — *Александр*
Объёмы небольшие: ~0,2 млн строк цен в год, до 10 тыс. запросов к API в сутки. Поэтому выбраны Python для загрузки и расчёта, FastAPI для API (требование: ответ ≤ 200 мс при 50 запросах в секунду), NumPy для расчёта окна в памяти, PostgreSQL 16 с партициями, React для веба и Docker Compose, чтобы всё разворачивалось одной командой внутри сети клиента. Spark, Kafka и подобные инструменты при таких объёмах не нужны. *Где:* семинар 4, раздел 7 (ASR).
